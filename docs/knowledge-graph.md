# 第 5 期 · 知识图谱原理笔记（knowledge-graph.md）

> 定位：面试武器库，与 `docs/hybrid-search.md` 同一风格。原理 → 本项目落地 → 面试怎么答。
> 代码：构建 `scripts/data/build_knowledge_graph.py`；查询 `backend/app/graph/knowledge_graph.py`；

## 1. 为什么需要知识图谱：向量检索的关系盲区

比喻版直觉：

- **向量检索像"词典"**：你问"台风是什么"，它把问题和所有知识块的意思比一比，捞出意思最近的——它懂**意思**，但每个知识块是孤立的，块与块之间的关系（台风引发风暴潮、风暴潮需要停止海上作业）在嵌入成一串数字时**丢失了**。
- **知识图谱像"地图"**：每个知识点是一个地点，关系是连接地点的路。问"台风的灾害链"，沿着路走就行——台风 →引发→ 风暴潮 →防御→ 停止海上作业。它存的就是**关系本身**。

失败模式对照（本项目实测，实验 6）：

| 问题类型 | 向量检索 | 图谱检索 |
|---------|---------|---------|
| "XX 是什么"（单点事实） | **强**（语义相似召回原文） | 弱（图谱只有骨架，无细节） |
| "XX 会引发什么，该怎么防"（关系链） | 弱（答案分散在多块，结构关系丢失） | **强**（多跳遍历直接成链） |

两者是**互补**不是替代——所以做成 LangGraph 的第四条通路（graph 意图），查图谱、空子图自动降级走向量知识路。

## 2. 属性图模型：图数据库的数据结构

Neo4j 用**属性图（property graph）**模型，三要素：

- **节点（node）**：一个实体，带标签（label，相当于类型）和属性（key-value）。本项目：`:Disaster {name: "台风"}`、`:Measure {name: "关紧门窗"}`
- **关系（relationship）**：两个节点之间的**有向**连接，带类型和属性。本项目：`(台风)-[:CAUSES]->(风暴潮)`、关系上带 `source` 属性记录来自哪张知识卡（溯源）
- **属性（property）**：节点/关系上的 key-value

为什么图数据库做关系查询比关系型数据库强（面试高频）：

SQL 做多跳查询要**自连接（self JOIN）**——每一跳多一个 JOIN，n 跳就是 n 层 JOIN，且查询计划随深度指数膨胀；图的存储是**邻接表/指针**，从节点出发沿关系走一步就是一次指针跳转，多跳遍历成本与"实际走过的边数"成正比，与全库大小无关。本项目数据量小看不出差距，但这是知识库扩到百万关系时图数据库的核心卖点。

## 3. Cypher：Neo4j 的声明式图查询语言

类比 SQL，但描述的是**图模式**（用ASCII art 画出来）：

```cypher
MERGE (h:Disaster {name: $head})          -- 按标签+属性找节点，不存在则创建（幂等）
MERGE (t:Phenomenon {name: $tail})
MERGE (h)-[r:CAUSES]->(t)                 -- 按模式找关系，不存在则创建
SET r.source = $source                    -- 关系上写属性（溯源）

MATCH (a)-[r]-(b) WHERE a.name IN $names  -- 无方向匹配 a 和 b 之间任意关系
RETURN type(r), a.name, b.name
```

本项目用到的核心能力：

- **MERGE 幂等写入**：按"标签+name"判节点存在、按三元组模式判关系存在——抽取脚本重复跑不产生重复数据（与 PG 的 `ON CONFLICT DO NOTHING` 同一设计思想）
- **MATCH 模式匹配**：`(a)-[r]-(b)` 单跳、`(a)-[r1]-(m)-[r2]-(b)` 两跳；`-[]-` 无方向（双向）、`->` 有方向
- **参数绑定**：`$names` 参数化查询值（与 SQL 参数绑定同一安全理由）；注意 **label 和关系类型不能参数化**（Cypher 语言限制），所以脚本里用白名单校验后再拼接——这是图查询里防注入的标准做法

## 4. 构建管线：LLM 信息抽取（Information Extraction）

知识图谱最难的不是查询，是**构建**（传统要人工标注三元组）。本项目用 LLM 抽取，工程要点：

1. **枚举约束**：Prompt 里把节点类型（5 种）和关系类型（5 种）全部枚举，只准从中选——杜绝自由发挥的类型体系
2. **JSON 结构化输出**：要求输出纯 JSON 数组；解析时用正则剥出 `[...]` 段容错（LLM 偶尔加前后缀废话）
3. **白名单二次校验**：LLM 输出不可信，入库前再过一遍白名单（类型 + 关系），不合法直接丢弃
4. **MERGE 幂等入库**：见上节

数据规模：预警知识卡 + 应急预案语料 → LLM 抽取三元组 → Neo4j（节点/关系数量见实验 6）。

## 5. 查询设计：词典实体匹配 + 多跳子图

**实体识别的坑（实验 6 实测教训）**：第一版把图谱全部实体名列进 Prompt 让 LLM 做受限选择——183 个实体时可用，语料扩到 890 个实体后清单塞爆 Prompt，LLM 选择质量崩掉、延迟涨到 30s。改**词典法**：节点名（≥2 字）作为子串直接和问题匹配（"台风" in "台风来了该怎么防御"），毫秒级、零成本、确定性。**能用词典/规则解决的匹配不要调 LLM**——LLM 留给真正需要语义理解的地方。

**子图查询**：三段 UNION 各自限额——①灾害链边（CAUSES/CAUSED_BY/BELONGS_TO）20 条 ②防御措施边（DEFENDS）15 条 ③二跳链边（只沿 CAUSES 扩展）15 条。分类限额的原因：台风一个节点挂了 413 条 DEFENDS 边（应急预案把政府组织动作也抽成了防御措施），单池无序 LIMIT 会全被组织措施占住，个人防御措施（关紧门窗等）被系统性埋掉——DEFENDS 段还要按来源排序（预警卡优先于预案）。

**方向还原**：入库的关系全部有向，查询用无方向匹配（用户问"防御"可能顺着问也可能反着问），取回后用 `CASE WHEN startNode(r) = a` 还原真实方向——三元组展示"台风 -[引发]-> 风暴潮"方向不能错。

## 6. 架构落位：LangGraph 第四通路

```
                ┌─ chitchat ──→ answer_chitchat ──────────┐
    classify ───┤                                         ├→ END
                ├─ weather ──→ fetch_weather → answer_weather
                ├─ graph ───→ query_graph ──→ answer_graph（空子图降级走 retrieve）
                └─ knowledge → retrieve → answer_knowledge
```

- 意图四分类（`chain.INTENT_PROMPT`）：出现"引发/导致/次生/连锁/防御措施"等关系链表述 → graph
- **降级设计**：实体未命中/子图为空 → 条件边自动转向 retrieve（向量知识路）——图谱是增强通路，它的问题不能挡住回答
- 展示 LangGraph 的扩展性：加一条通路 = 加两个节点 + 两条边，主流程零改动（当初选状态机的理由在此兑现）

## 7. 消融实验数据（2026-08-25，docs/experiments.md 实验 6）

构建规模：168 块语料（预警知识卡 + 应急预案）→ LLM 抽取 1081 条三元组 → **890 节点 + 1018 关系**（Measure 699 / Phenomenon 70 / Disaster 57 / Condition 36 / Signal 28；DEFENDS 812 / CAUSES 122 / BELONGS_TO 54 / CAUSED_BY 27 / ACCOMPANIES 3）。

5 个关系类问题，图谱 vs 向量混合检索（第 4 期最强基线）：

| 指标 | 图谱 | 向量混合 | 量化 |
|------|------|---------|------|
| 期望实体覆盖 | 20/21（95.2%） | 19/21（90.5%） | 相对 +5.3%（(20−19)/19） |
| 检索延迟均值 | 0.04s | 1.39s | **快约 34.7 倍**（降 97.1%） |
| 素材形态 | 结构化三元组（自带关系方向） | 无结构文本块 | 质的差距：LLM 沿链推理 vs 自行重组 |

结论：覆盖相当、延迟碾压、形态更优——图谱与向量是**互补**（意图路由分流 + 空子图降级），不是替代。

## 8. 面试自问自答

**Q1：为什么用图数据库而不是继续用 PostgreSQL 存关系表？**
A：多跳关系查询的成本模型不同。SQL 做 n 跳要 n 层自 JOIN，成本随深度指数增长；图的遍历成本只与实际走过的边数成正比，与全库规模无关。本项目当前量级（几百关系）确实 PG 也能做，但知识库要持续扩充、灾害链查询天然是多跳场景（灾害→次生→防御→物资），提前用对数据结构。这也是"技术栈选型要匹配数据形态"的例子：文本块用向量库、结构化知识用图、关系型数据用 PG——三种数据形态三套存储。

**Q2：知识图谱怎么构建的？人工标注吗？**
A：LLM 信息抽取。预警知识卡和应急预案语料逐块送 LLM，Prompt 里枚举约束节点类型（Disaster/Phenomenon/Measure/Condition/Signal）和关系类型（CAUSES/DEFENDS/CAUSED_BY/BELONGS_TO/ACCOMPANIES），要求输出 JSON 三元组；入库前白名单二次校验，Cypher MERGE 幂等写入（重复跑不产生重复数据）。传统人工标注是这成本的几十倍。

**Q3：实体识别怎么做的？为什么不用 LLM？**
A：词典法——节点名（≥2 字）作为子串和问题直接匹配，毫秒级。实测教训：第一版把全部实体名列进 Prompt 让 LLM 受限选择，183 实体时可用，扩到 890 后清单过长导致选择质量崩掉且延迟 30s——**能用词典/规则解决的匹配不要调 LLM**。LLM 的语义理解留给"问题改写"这种真需要它的环节。

**Q4：图谱查询挂了/没查到怎么办？**
A：双层降级——实体识别失败返回空列表、子图为空时，LangGraph 条件边自动把路由切到向量知识路（retrieve 节点）；图谱服务本身故障也被 try 住不炸主链路。增强通路的故障只能降低体验，不能中断服务（fail-safe）。

**Q5：Cypher 的 MERGE 和 SQL 的 INSERT 有什么区别？**
A：MERGE 是"存在即复用、不存在即创建"——按给定的模式（标签+属性/关系模式）先 MATCH 再 CREATE，天然幂等；INSERT 是无条件插入，重复执行产生重复行（要配 ON CONFLICT 才幂等）。本项目抽取脚本可重复跑全靠 MERGE。

**Q6：图查询怎么防注入？**
A：查询值全部参数绑定（$names），和 SQL 同一原则。但 Cypher 的 label 和关系类型不能参数化（语言限制），动态拼 label 时必须白名单校验——本项目节点类型和关系类型都是固定枚举，Prompt 约束 + 入库前白名单双保险。

**Q7：GraphRAG 和普通 RAG 的区别？（趋势题）**
A：普通 RAG 检索独立文本块，块间结构关系在嵌入时丢失；GraphRAG 把知识组织成图，检索时取子图（带结构的多个三元组），LLM 沿关系链推理。适合多跳问题（"A 引发的 B 怎么防"）。微软的 GraphRAG 论文是先用 LLM 全库抽实体建图再做社区摘要，本项目是轻量版：只对高关系密度的语料（预警卡+预案）建图，按意图路由分流——不是所有问题都需要图。

**Q8：为什么 DEFENDS 关系方向是"灾害 → 措施"？**
A：抽取 Prompt 里固定了方向约定（灾害 DEFENDS 措施 = 防御该灾害的措施），否则 LLM 每次抽取方向随机（有时"措施 防御 灾害"有时反着），图里会出现语义混乱的双向边。关系方向是图建模的一部分，必须在抽取前定死——这是 LLM 构建结构化数据的基本纪律：枚举约束 + 方向约定。

**Q9：子图为什么限制 40 条三元组？**
A：子图是注入 LLM prompt 的上下文，太大溢出、太小丢信息。实测台风二跳子图 40+ 条已覆盖主要灾害链和防御措施。工程上这是"检索结果的上下文预算"问题，和向量检索 top-k 一个道理——k 不是越大越好。

**Q10：这套图谱怎么扩？**
A：三个方向——①语料：把台风/暴雨专题网页和教材章节也过抽取管线（MERGE 幂等，直接重跑）；②深度：三跳以上（灾害→次生→次次生）改变长路径或调整两段 UNION 的跳数；③应用：预警推送时可反查图（"该预警对应灾害的全部防御措施"）。扩语料是零代码改动的（抽取脚本按 source 过滤条件放宽即可）。
