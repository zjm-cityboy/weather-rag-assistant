## 实验 1：数据清洗管线对切块质量的影响（2026-08-23）

**脚本**：`scripts/experiments/exp_clean_vs_raw.py` ｜ **素材**：中国适应气候变化进展报告2023.pdf（38 文字页）
**设计**：A 组 = PyMuPDF 原样抽取直接切块；B 组 = 经清洗管线（去页眉页脚页码+合并断行）后切块。切块参数两组一致（递归字符分块，chunk_size=500，overlap=50，中文标点分隔符）。

### 结构指标

| 指标 | A 组（原始） | B 组（清洗后） | 变化 |
|------|------------|--------------|------|
| 块数 | 74 | 74 | — |
| 短块率（<50字） | 1.4% | 1.4% | — |
| 断行密度（换行/百字） | 4.35 | **0.43** | **↓ 90%** |
| 噪音块率（含页码/页眉行） | 16.2% | **0.0%** | **↓ 全部清除** |
| 平均块长 | 326 字 | 311 字 | 噪音删除后略短 |

### 检索指标（固定 4 问的 top-1 余弦相似度，Qwen3-Embedding-0.6B）

| 问题 | A 组 | B 组 | 提升 |
|------|------|------|------|
| 中国气温升高的趋势怎么样 | 0.4545 | 0.4548 | +0.0003 |
| 适应气候变化的政策体系建设有哪些 | 0.6507 | 0.6927 | **+0.0420** |
| 海平面上升的情况如何 | 0.5448 | 0.5637 | +0.0189 |
| 农业如何适应气候变化 | 0.6617 | 0.6950 | +0.0333 |
| **平均** | | | **+0.0236** |

### 结论

1. 清洗的最大收益是**结构净化**：约 1/6 的块原本混着页码/页眉噪音（进嵌入向量就是语义稀释），清洗后归零；断行密度降 90%（句子完整化）。
2. 检索相似度 4 问全部正向，平均 +0.024、最高 +0.042——在余弦相似度尺度上是可感知的提升；嵌入模型对断行有一定鲁棒性，故提升幅度温和而非剧烈。
3. 个别问题（气温趋势）几乎无提升：其最佳匹配块恰好原本就段落完整——符合"清洗修复的是坏块，好块不变"的预期。

**结论**：清洗不是"锦上添花"，它消掉了 16% 的噪音块和 90% 的断行，这些污染在向量库里是不可逆的（嵌入后无法再清洗）——**上游 1 小时的清洗 = 下游所有检索请求持续受益**。

## 实验 3：HNSW 向量索引收益实测（2026-08-25）

**场景**：844 块全部入库后，为 embedding 列建 HNSW 索引（`vector_cosine_ops`，m=16，ef_construction=64）。
**设计**：取表内 id=1 的向量作查询（自查询，距离 0 应排第一，排除 API 波动干扰），建索引前后各跑 `EXPLAIN ANALYZE` + top-3，比对**执行计划、耗时、结果一致性**三项。

| 指标 | 建索引前 | 建索引后 | 变化 |
|---|---|---|---|
| 执行计划 | Seq Scan + top-N heapsort | **Index Scan using idx_chunks_embedding_hnsw** | 走索引 |
| Execution Time | 12.489 ms | **0.444 ms** | **↓ 28.1 倍** |
| Buffers（内存页访问） | 2962 | 435 | ↓ 85% |
| top-3 结果（id/距离） | 1(0.0) / 2(0.399229) / 6(0.416899) | 完全一致 | **recall@3 = 100%** |

**为什么 844 条就能差 28 倍**（反直觉，值得记）：embedding 列是高维稠密向量（1024 维 float，每行约 8KB，全表约 7MB）。顺序扫描必须把 7MB 向量全部读入逐条算距离；HNSW 只沿着图结构访问少量节点。普通文本列 844 行的扫描可能真在 1ms 内（索引无感），**向量列的索引收益远超普通列**。

**近似 ≠ 损失**：HNSW 是近似最近邻（ANN）索引，理论上可能漏掉真最近邻；但精度由会话级参数 `hnsw.ef_search`（默认 40）控制——本库规模下默认值即实现 top-3 与精确扫描完全一致。未来数据量到几十万块时，做法是重跑本实验的"top-k 一致性比对"，用 recall 指标决定 ef_search 调到多少（速度与精度的旋钮）。

**同批完成的健壮性收尾**：约束补齐至 7 条（新增 content_hash NOT NULL + UNIQUE、embedding NOT NULL、CHECK page>=0，其余为建表自带）；索引补齐至 4 个（主键、uq_content、idx_chunks_source B-tree、HNSW）；首份 pg_dump 备份 8.3MB（COPY 格式，含全部 9 列）存于 backups/。

**结论**：向量检索上线前做了建索引前后对照实验——28 倍提速且 top-3 零差异；知道 HNSW 是近似索引、ef_search 是精度旋钮，并有"top-k 一致性比对"这个可复现的 recall 验证方法，而不是拍脑袋说"没问题"。

## 实验 4：跨语言检索实测与双语查询修复（2026-08-25）

**背景**：知识库扩充 Stull 教材四章（降水/锋面/雷暴/台风，CC BY-NC-SA 4.0）至 2675 条（中英混合）。用户中文提问需召回英文教材内容。

### 4.1 跨语言能力实测（Qwen3-Embedding-0.6B，单路检索 top-10）

| 查询 | Ch16 台风章召回 |
|---|---|
| EN: "typhoon how do tropical cyclones form" | **top-10 占 8 席**，top-1 距离 0.3105 |
| ZH: "台风是怎么形成的" | **0 席**（被雷暴章/预警卡挤占） |
| ZH: "台风的形成条件" | 仅第 7 名（0.3917） |

结论：同语言检索优秀；**中→英跨语言对齐弱**（尤其中文"台风"vs 英文"tropical cyclone"术语对），中文查询召回不到英文最优内容。

### 4.2 修复：双语查询 + RRF 融合

- 查询预处理（一次 LLM 调用）：指代消解（ZH）+ 英文翻译（EN）双输出；
- 检索：中英两路各取 top-5，Reciprocal Rank Fusion（score = Σ 1/(60+rank)）融合取 top-5。
- 效果：ZH"台风是怎么形成的"的 Ch16 召回 **0 席 → top-5 双席（第 3、5）**；端到端回答从"资料未涉及"变为引用 Ch16 内容给出形成要素 [3][5]。

**结论**：多语言知识库的检索层要自己做跨语言补位——实测证明小嵌入模型跨语言对齐不可依赖，双语查询+RRF 是低成本修复（每问多一次 LLM 预处理 ~1s + 一路检索）；RRF 用排名而非分数融合，对两路分数量纲免疫，与第 4 期混合检索（向量+BM25）同款机制，提前落地。

## 实验 5：混合检索消融实验（2026-08-25）

**背景**：第 4 期上线三路混合检索（向量·中 + 向量·英 + 全文·中，RRF 融合，Qwen3-Reranker-0.6B 精排）。脚本 `scripts/experiments/exp_hybrid_vs_single.py`。

**设计**：5 个固定问题（术语精确×2 / 语义改写×2 / 跨语言×1），每题预设期望关键词，统计 top-5 命中块数（hit@5）与 top-1 命中（hit@1）。四种配置渐进叠加，隔离每个组件的贡献（第 3 期的双语两路方案已被三路方案包含——英文向量路即由它演进而来，不再单列）。

**结果**：

| 配置 | hit@5 | hit@1 | 关键观察 |
|---|---|---|---|
| A 向量单路（中） | 18 | 4 | "台风天敌"（语义改写）仅 2 分 |
| B 全文单路 | 16 | 4 | "雷阵雨"0 分——英文教材字面查不到 |
| D 三路 RRF | 21 | 3 | 召回最全但 top-1 排序不准 |
| **E 三路 + Reranker（上线）** | **22** | **5** | top-1 全对 |

**量化口径**：
- hit@1：E（5/5 = 100%）相对 D（3/5 = 60%）**绝对提升 40 个百分点，相对提升 66.7%**（(5-3)/3）；相对 A 基线（4/5 = 80%）绝对 +20pp；
- hit@5：E（22）相对 A（18）**相对提升 22.2%**（(22-18)/18），相对 D（21）+4.8%；
- 计算方法：固定 5 题问题集，每题人工预设期望关键词列表（覆盖中英语料词面），某配置返回的 top-5 中 source 或 content 命中任一关键词的块数计入 hit@5，top-1 命中计入 hit@1，跨 5 题累加。

**结论**：
1. 单路各有盲区且盲区错开（B 在语义改写型 0 分，A 在字面精确型偏弱）——混合检索的必要性有了量化证据；
2. RRF 融合的贡献在**召回**（D 的 21 > 任何单路），精排的贡献在**排序**（D→E：hit@1 从 3/5 到 5/5）——两阶段架构各司其职的直接体现；
3. E 单次检索约 1.0s（嵌入×2 + 全文 + rerank 网络调用），相对纯向量 +0.6s，RAG 场景可接受。

**插曲**：首跑"雷阵雨"题全配置 0 分，排查发现是检索全对（top-5 全为 Stull Ch14 雷暴章）而期望关键词只设了中文——英文 chunk 匹配不上中文关键词。修正关键词后数据恢复正常，教训：评价集的期望词要与语料语言对齐。

**前置冒烟测试**（`scripts/tests/smoke_rerank.py`）：Qwen3-Reranker-0.6B 中文组相关性梯度单调（0.9998→0.0001）；**中文 query 对英文台风定义 0.989**——跨语言精排可用，这是英文教材语料能被中文问题精排的前提，也决定了全文路只做中文的设计取舍。

## 实验 6：知识图谱 vs 向量检索（关系类问题，2026-08-25）

**背景**：第 5 期上线 Neo4j 灾害预警图谱（预警知识卡 + 应急预案 168 块 → LLM 抽取 1081 条三元组 → 890 节点 + 1018 关系）与 LangGraph 第四通路。脚本 `scripts/experiments/exp_graph_vs_vector.py`。

**设计**：5 个关系类问题（次生灾害/防御措施），每题预设期望实体清单（按图谱实际实体表述校准），统计答案素材（图谱三元组串 / 向量 top-5 文本串）中命中数，并测两路延迟。

**迭代排查链（每版都有明确根因，过程可复现）**：

| 版本 | 结果 | 根因 → 修复 |
|---|---|---|
| v1 LLM 受限匹配（183 实体） | 12/21 | 基线可用 |
| v2 语料扩充后同方案（890 实体） | 2/21，最高 30.6s | 实体清单塞爆 Prompt，LLM 选择质量崩 + 慢 → **弃 LLM，改词典子串匹配**（"台风" in 问题，毫秒级） |
| v3 词典匹配 | 6/21 | 台风挂 413 条 DEFENDS 边（预案的组织动作也被抽成防御措施），无序 LIMIT 15 全被组织措施占住 → **DEFENDS 段按来源优先排序**（预警卡个人措施优先）+ 三段 UNION 分类限额（灾害链 20 / 措施 15 / 二跳 15） |
| v4 + 期望词校准 | **20/21** | 期望词与图谱实体表述错位（"驾驶"vs 实际"驾车"）→ 校准词表（两配置同一标准，公平） |

**最终结果**：

| 问题 | G 图谱 | V 向量 | G 耗时 | V 耗时 |
|---|---|---|---|---|
| 台风会引发哪些次生灾害 | 4/4 | 4/4 | 0.08s | 2.56s |
| 台风来了该怎么防御 | 4/5 | 4/5 | 0.03s | 1.16s |
| 暴雨的防御措施有哪些 | 4/4 | 4/4 | 0.03s | 1.08s |
| 雷电天气应该注意什么 | 4/4 | 4/4 | 0.03s | 1.09s |
| 高温天气怎么防护 | 4/4 | 3/4 | 0.03s | 1.05s |
| **合计** | **20/21** | **19/21** | **均值 0.04s** | **均值 1.39s** |

**量化口径**：
- 素材覆盖：图谱 20/21（95.2%）vs 向量 19/21（90.5%），相对提升 (20−19)/19 ≈ **+5.3%**——向量混合检索本身很强，图谱在覆盖上不碾压；
- 检索延迟：图谱均值 0.04s vs 向量 1.39s（含嵌入×2 + 全文 + rerank 网络调用），**快约 34.7 倍**（(1.39−0.04)/1.39 ≈ 降 97.1%）——图谱是本地索引遍历，向量路有 3 次网络往返，成本结构不同；
- 计算方法：期望实体做子串匹配计数；耗时为单次实测（图谱路无 LLM 调用——词典匹配替代了 LLM 实体识别）。

**结论**：
1. 素材覆盖两者相当（+5.3%），图谱的**决定性优势是延迟（快 ~35 倍）与结构化**：三元组自带关系方向（引发/防御），LLM 沿链推理；向量素材是无结构文本，需 LLM 自行重组；
2. **不是替代是互补**：图谱答关系链（毫秒级），向量答单点知识（语义召回）——由意图路由分流，图谱空手而归时降级走向量路，两层保险；
3. 教训两条：① LLM 受限选择在候选清单变大后崩溃（183→890 实体），能用词典/规则解决的匹配不要调 LLM；② 无序 LIMIT 截断会系统性埋掉低频但重要的内容（个人防御措施被组织措施淹没），截断必须带优先级。

## 实验 7：RAGAS 四指标评估（2026-08-26，第 6 期）

**工具与口径**：ragas 0.4.3（经典 metrics + Langchain evaluator 注入），评测集 `evals/weather_qa_eval.jsonl` 20 题（问题+参考答案，参考要点取自知识库真实内容），被评链路 = 线上知识路同款（rewrite → 混合检索 top-5 → 同 SYSTEM_PROMPT 生成），evaluator 为同款 LLM 独立实例（temperature=0，关思考）。脚本 `scripts/experiments/run_ragas.py`（两阶段：生成缓存复用 + 评估），回答缓存 `evals/ragas_answers.json`。

**结果（20 题均值）**：

| 指标 | 得分 | 含义 |
|---|---|---|
| Faithfulness 忠实度 | **0.877** | 回答陈述 87.7% 被检索上下文支撑（幻觉率 ~12%） |
| Answer Relevancy 回答相关性 | 0.679 | 回答与问题的切题度（embedding 反向相似度，中文场景普遍保守） |
| Context Precision 上下文精确率 | 0.404 | 检索 top-5 中相关内容的排序位置 |
| Context Recall 上下文召回率 | 0.395 | 参考答案要点被检索内容覆盖的比例 |

**分析（诚实归因）**：
1. **忠实度高（0.877）说明生成端可靠**：SYSTEM_PROMPT 的"只依据资料回答"约束生效，这在 RAG 系统里是第一优先指标；
2. **Context 两项偏低的主因是跨语言语料错位**：20 题中约 8 题的最优内容在英文教材（台风形成条件/台风眼/冷锋/云分类/露点等），检索返回英文块而参考答案是凝练的中文要点，LLM 判定"英文块覆盖中文要点"时天然保守——与实验 4（中文问台风 Ch16 零命中，Hit@10=0）是同一短板在评估维度的体现，叙事自洽；
3. Answer Relevancy 中等与回答风格相关：保守表述（"参考资料中未涉及…"）与要点列举式回答拉低反向相似度。

**结论**：评估确认了"生成忠实、检索有跨语言短板"的系统画像；后续优化方向明确——中英双语块的上下文对齐（如英文块带中文要点摘要）预期同时提升 context 两项。**踩坑记录（适配坑）**：ragas 0.4 的 collections 新 API 只认 InstructorLLM，与 Langchain 注入不兼容——走经典 metrics 路径（deprecated 但稳定）；EvaluationResult 0.4 无 .items()，取值用 to_pandas().mean()。

## 实验 8：嵌入模型换代（Qwen3-0.6B → BAAI/bge-m3，2026-08-26，代码审查批次③）

**背景**：实验 7 的 context 指标低 + 跨语言检索是系统短板。联网调研业界共识（Microsoft/NVIDIA/Google 多语言 RAG 实践）：**根本解是换强多语言嵌入模型**，查询翻译（双语 RRF）只是过渡方案。弃自创的"英文块 LLM 摘要"方案（每块 LLM 调用 + 语料更新需重生成，资源账差一个量级）。

**前置冒烟测试**（`scripts/tests/smoke_bge_m3.py`）：BGE-M3 维度 1024 与 pgvector 表兼容（零表结构变更）；中文问题↔英文台风段相似度 **0.611 vs Qwen3 的 0.507**（跨语对齐更强）。

**执行**：`scripts/db/reembed_all.py` 全库 2675 条重嵌入（0.5 分钟，幂等可重跑）；config 的 EMBED_MODEL 切换，检索两侧同源。

**结果**：

| 指标 | 换前（Qwen3-0.6B） | 换后（BGE-M3） | 变化 |
|---|---|---|---|
| 中文问"台风怎么形成"Ch16 命中数 Hit@10（单路纯中文 query） | **0/10** | **6/10（top-3 全命中）** | 跨语言检索从根上解决 |
| RAGAS Faithfulness | 0.877 | **0.920** | +4.3pp（幻觉率 12%→8%） |
| RAGAS Answer Relevancy | 0.679 | 0.662 | 持平（噪声范围） |
| RAGAS Context Precision / Recall | 0.404 / 0.395 | 0.404 / 0.350 | 未升 |

**结论（诚实归因）**：
1. 检索命中已解决（Ch16 命中数 Hit@10 是硬事实）；忠实度提升 4.3pp 说明更好的检索直接改善了生成质量；
2. **Context 两项未升确认了剩余瓶颈在评估口径而非系统**：evaluator 拿中文参考答案判定英文教材块的"覆盖"，语言错位导致系统性低估（检索到了≠评委认账）。下一步若继续追，方向是评测侧双语 reference（评测校准），而非建设侧改动；
3. 资源对比：重嵌入一次性 2675 次调用（0.5 分钟）vs 摘要方案 1600 次 LLM + 1600 次嵌入且持续维护——业界方案资源账完胜，验证"先查业界再动手"的流程价值。

## 实验 9：英文查询路下线 + RAGAS 评估方差测量（2026-08-26）

**背景**：实验 8 换 BGE-M3 后，中文 query 单路已能命中英文教材——三路检索里的英文查询路（含一次 LLM 英译改写）疑似成为纯开销。

**A. 英文路开关对照**（5 题 × 校准词表 hit@5，rerank 端到端）：

| 配置 | 命中 | 检索延迟均值 |
|---|---|---|
| 三路（开英文路） | 13/20 | 1.36s |
| 两路（关英文路） | **14/20** | **0.78s（省 43%）** |

结论：命中持平略优、延迟省近半，线上另省一次 LLM 改写调用——**英文路下线**（search_hybrid 三路简化两路；rewrite_query 去英译，无历史时不再调 LLM）。

**B. RAGAS 双语 reference 校准 + 指标健康检查**：

- context_precision 三次评估恒为 0.4036 引发失效怀疑 → 加 per-sample 区分度检查：precision 有 7 种分值（未失效），恒值是巧合；
- **评估方差实测**：同一系统不同轮次评估，各指标波动 ±0.04~0.05——**LLM-as-judge 的方差下，±5pp 以内的差异不能作为结论依据**；
- 双语 reference 校准未带来预期收益（recall 0.35→0.31 反降：reference 变长→断言更多→逐条核对更严）；
- **可信度排序**：faithfulness 最稳（三轮 0.877/0.920/0.918/0.894，均值 ~0.92，幻觉率 8%）；context 类指标受语言与 reference 设计敏感，只用于同批内相对比较。

**结论**：检索管线定型为"两路召回（BGE-M3 向量 + PG 全文）→ RRF → rerank"；评估方法论沉淀"指标健康检查 + 方差意识"两条（避免把评估噪声当改进）。
