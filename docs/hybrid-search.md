## 1. 为什么需要混合检索：两种检索的失败模式互补

先建立直觉（比喻版）：

- **向量检索像"听意思"**：把问题和文档各压缩成一个 1024 维的"意思点"，按意思的远近找。你问"台风的天敌"，它能找到写"冷空气和垂直风切变摧毁热带气旋"的文档——字面完全不同，但意思近。
- **全文检索像"对暗号"**：一个词一个词精确对上才算命中。你问"3小时内降雨量达100毫米"，它能精准锁住含这个量级标准的文档，一个字都不含糊。

**两种失败模式**（消融实验实证，见第 6 节）：

| 场景 | 向量检索 | 全文检索 |
|------|---------|---------|
| 术语/编号精确（"100毫米""红色预警"） | 弱——专有词被压进向量里"糊"掉 | **强**——字面精确命中 |
| 同义改写（"天敌"≈"削弱因素"） | **强**——语义空间距离近 | 弱——字面不同就查不到 |
| 冷门词（语料中罕见的专业词） | 弱——训练时见得少，向量不准 | **强**——倒排索引一查一个准 |
| 跨语言（中文问题查英文教材） | 中——嵌入对齐不完美 | 弱——中英词面完全不同 |

**结论**：单路都有盲区，而盲区恰好错开 → 同时召回、融合排序，就是混合检索（hybrid search）。
Elasticsearch 8.x、Azure AI Search、Weaviate 等主流引擎都内置了 hybrid 检索，这是业界共识方案，不是项目炫技。

## 2. 词法检索原理：从 tf-idf 到 BM25

### 2.1 tf-idf：词的重要度

核心思想：一个词对某文档越"专属"，权重越高。

- **tf**（term frequency，词频）：词在本文档出现越多 → 越重要
- **idf**（inverse document frequency，逆文档频率）：词在**全库**出现得越少 → 越有区分度
  - "的"出现在几乎所有文档 → idf ≈ 0，无区分度
  - "垂直风切变"只出现在几十个文档 → idf 很高，一命中就说明相关

### 2.2 BM25：tf-idf 的两个关键修正

BM25（Okapi BM25，1994）是目前最主流的词法相关性评分函数（Elasticsearch 默认）：

```
score(q, d) = Σ_i  IDF(q_i) · [ tf(q_i,d) · (k1+1) ] / [ tf(q_i,d) + k1·(1 − b + b·|d|/avgdl) ]
```

逐项拆解（面试要能指着公式讲）：

| 组件 | 作用 | 直觉 |
|------|------|------|
| `k1`（词频饱和，典型 1.2~2.0） | 词频收益递减 | 词出现 3 次比 1 次相关，但 30 次不比 3 次相关 10 倍——tf-idf 里词频线性增长，BM25 加了"天花板" |
| `b`（长度归一，0~1，典型 0.75） | 长文档"稀释"惩罚 | 同样出现 3 次"台风"，在 100 字短文里比在 1 万字长文里更能说明主题 |
| `avgdl` | 全库平均文档长度 | 归一化的参照系 |

一句话总结：**BM25 = idf 加权 × 带饱和的词频 × 带长度归一的文档分**。

### 2.3 本项目的诚实声明：PG 的 ts_rank_cd ≠ 严格 BM25

PostgreSQL 原生全文检索的排序函数是 `ts_rank_cd`（cd = cover density，覆盖密度），它属于 tf-idf 家族：

- 计算词频，并额外考虑**查询词在文档中出现的紧密程度**（词挨得越近分越高）
- **没有** BM25 的 k1 饱和曲线和 b 长度归一（PG 22.x 及之前都没有内置 BM25）

本项目选型理由：pgvector 已在库，PG 全文检索**零新增组件**即可获得词法分支；对 2675 条小语料，ts_rank_cd 与 BM25 的排序差异远小于"有没有词法分支"的差异。真需要严格 BM25 的方案是 ParadeDB 的 `pg_search` 扩展或 Elasticsearch——面试时能说清这个差异与取舍，比背"我用了 BM25"更加分。

> **简历/面试措辞**：写"PostgreSQL 全文检索（tsvector/GIN 索引）与向量检索 RRF 混合，cross-encoder 精排"，不写"BM25"冒充。

### 2.4 中文分词：为什么必须外置 jieba

PG 的全文检索按**空格切词**（对英文天然成立）。中文"台风预警信号"没有空格，`simple` 配置会把整句当成**一个** lexeme——查询"台风"永远匹配不上"台风预警信号"这个"长词"。

所以链路是：

```
入库：content --jieba--> "台风 预警 信号 ..."（空格分隔词串）--PG--> tsvector 生成列
查询：query   --jieba--> 同款分词 --> tsquery（词 & 词 & 词）
匹配：tsv @@ query（GIN 索引加速）
```

两端分词器必须一致，否则词面对不上。Docker 里装 zhparser 扩展也能在 PG 内做中文分词，但要换镜像重起库；应用层 jieba 是侵入最小的工程选择。

### 2.5 AND/OR 两级匹配（本项目实际踩的坑）

`plainto_tsquery` 把所有词按 **AND** 连接——"台风预警信号分几级"分词后含"几级"，文档里没有"几级"二字 → **全军覆没**。

修复：① 停用词过滤（"什么/怎么/的/几"等疑问词虚词不入查询）；② AND 空结果自动降级 OR（任一词命中即可，ts_rank_cd 排序仍偏向命中词多的文档）。这是 PG 全文检索处理自然语言查询的标准实践。

## 3. RRF：多路结果怎么融合

### 3.1 为什么不能直接比分数

三路召回的分数**量纲完全不同**：

| 路 | 分数 | 范围 | 含义 |
|----|------|------|------|
| 向量 | 余弦**距离** | 0~2（越小越好） | 语义相似度 |
| 全文 | ts_rank_cd | 0~正无穷（越大越好） | 词法相关度 |
| 精排 | relevance_score | 0~1（越大越好） | 交叉编码相关概率 |

方向都相反（距离越小越好 vs 分数越大越好），硬拉到同一尺度（min-max 归一化）对每路的分数分布敏感：一路出了一个极端高分，其他路的分数会被压扁。

### 3.2 RRF 公式：只用排名

Reciprocal Rank Fusion（2009 论文提出，Elasticsearch、Weaviate 等采用）：

```
RRF_score(d) = Σ_{每一路 r}  1 / (k + rank_r(d))
```

- `rank_r(d)`：文档 d 在第 r 路里的名次（第 1 名 = 1）
- `k`：平滑常数，**业界标准 60**（Elasticsearch 默认同值）
- 一个文档被多路同时召回 → 分数累加 → 这正是"两路都觉得行"的文档该排前面

**为什么 k=60**：让第 1 名（1/61）和第 2 名（1/62）的差距不至于过大——排名本身有噪声（第 3 和第 4 可能实力相当），k 越大排序越"平缓"，单路的偶发失误对最终融合影响越小。k=60 时头部名次仍有区分度、又不会一票定生死。

## 4. Reranker 精排：cross-encoder vs bi-encoder（面试高频！）

### 4.1 结构差异

**Bi-encoder（双塔，嵌入检索用的结构）**：

```
query ──编码器──> 向量 q ─┐
                          ├─ 余弦距离
文档 ──编码器──> 向量 d ─┘   （文档向量可离线预计算！）
```

query 和文档**分别**过编码器，互相"看不见"对方。文档向量入库时算好存 pgvector，查询时只算 query 一个向量，然后 ANN 索引（HNSW）毫秒级扫全库 → **快，适合召回，但交互浅**（模型无法针对这个具体问题关注文档的具体部分）。

**Cross-encoder（交叉编码，Reranker 用的结构）**：

```
[CLS] query [SEP] 文档 ──────> 同一个 Transformer ──────> 相关性分数
```

query 和文档**拼成一个序列**一起送入模型，自注意力让问题里的每个词直接"看到"文档里的每个词——"天敌"能和文档里的"冷空气、垂直风切变"逐词交互判断。**精度显著更高，但每对 (query, 文档) 都要现算一次，无法预计算** → 慢且贵，不可能对 2675 条全库跑。

### 4.2 两阶段架构：召回 + 精排（信息检索标准范式）

```
全库 2675 条 ──[向量×2 + 全文]──> 候选 20 条 ──[RRF 融合]──> ──[Reranker]──> 最终 top-5
                 毫秒级，求全（不漏）                          ~0.5s，求准（排对）
```

- **召回**（recall）：bi-encoder + ANN 索引，快、能扫全库，目标是不漏掉相关文档（宁多勿漏）
- **精排**（rerank）：cross-encoder 只对 top-20 候选现算，目标是把最相关的排到最前

这就是"漏斗"：宽进（20 条）严出（5 条）。学术名 CDR（cascade ranking）思想，Google/Bing 搜索同款范式。

### 4.3 本项目落地

- 模型：Qwen3-Reranker-0.6B（硅基流动 `/rerank` 接口，OpenAI 兼容生态外挂能力）
- 输入：原始中文问题 + RRF 融合后的 20 条候选；输出按 relevance_score 降序取 top-5
- **降级策略**：rerank 调用失败降级用 RRF 排序（增强项故障不阻断主链路——工程上的 fail-safe）

### 4.4 为什么精排是必要的（消融数据说话）

第 6 节实验：三路 RRF（D）hit@1 = 3/5，加精排（E）= **5/5**。RRF 解决"该进前 5 的别漏"，精排解决"进了前 5 的排对位置"——LLM 生成时上下文里排第 1 的资料权重最高，top-1 错了答案就偏。

## 6. 消融实验数据（2026-08-25，docs/experiments.md 实验 5）

5 个固定问题（术语精确×2 / 语义改写×2 / 跨语言×1），指标 hit@5 / hit@1：

| 配置 | hit@5 | hit@1 | 说明 |
|------|-------|-------|------|
| A 向量单路（中文） | 18 | 4 | "台风天敌"仅 2——语义改写也会漏 |
| B 全文单路 | 16 | 4 | "雷阵雨"0 分——字面查不到英文教材 |
| D 三路 RRF | 21 | 3 | 召回最全，但排序不准 |
| **E 三路 + 精排（上线）** | **22** | **5** | top-1 全对 |

**量化口径（怎么算的）**：hit@1 = 该配置 5 题中 top-1 命中期望关键词的题数 / 5。E=5/5（100%）对比 D=3/5（60%）——绝对提升 40 个百分点，相对提升 (5-3)/3 ≈ **66.7%**；对比 A 基线 4/5（80%）绝对 +20pp。hit@5 按同法累加块数，E 相对 A 提升 (22-18)/18 ≈ **22.2%**。

耗时：E 单次约 1.0s（嵌入×2 + 全文 + rerank；不含 LLM 生成）。

## 7. 面试自问自答

**Q1：为什么不用 BM25 而用 PG 的 ts_rank_cd？**
A：严格说是选了 PG 原生全文检索而不是严格 BM25。ts_rank_cd 属于 tf-idf 家族（带覆盖密度），缺 BM25 的 k1 饱和与 b 长度归一；对本项目 2675 条语料，这个排序差异的影响远小于"有无词法分支"，且零新增组件（pgvector 已在库）。要严格 BM25 会选 ParadeDB pg_search 或 Elasticsearch。关键是能讲出 BM25 公式两项修正的含义（见 2.2）。

**Q2：RRF 为什么用 60？为什么不用分数归一化？**
A：k=60 是提出方与 Elasticsearch 采用的标准值，作用是平滑排名噪声（第 1 名 1/61、第 2 名 1/62，差距不至于一票定生死）。不用分数归一化是因为多路分数量纲不同（余弦距离 0~2 越小越好、ts_rank_cd 0~∞ 越大越好），归一化对分数分布敏感，RRF 只用排名天然免疫。

**Q3：reranker 和 embedding 检索的区别？（必考）**
A：bi-encoder（嵌入）双塔分开编码可预计算、毫秒级扫全库，适合召回但交互浅；cross-encoder（reranker）把 query 和文档拼接后同过一个大模型，逐词注意力交互，精度高但每对现算、无法预计算。所以工程上两阶段：召回求全（top-20）、精排求准（top-5）。本项目消融：+精排把 hit@1 从 3/5 提到 5/5。

**Q4：中文全文检索为什么需要 jieba？PG 自己不行吗？**
A：PG 的 simple 配置按空格切词，中文没有空格，整句会被当成一个 lexeme 查不到。所以应用层 jieba 分词后空格连接入库（tsvector 生成列），查询端同款分词。替代方案 zhparser 扩展要换 Docker 镜像，侵入大。两端分词器必须一致。

**Q5：AND 匹配为什么会全军覆没？怎么解决？**
A：用户问题分词后含"几级/什么"等疑问词，plainto_tsquery 是 AND 语义，文档缺任何一个词就不命中。解决两级：停用词过滤（疑问词虚词不入查询）+ AND 空结果降级 OR（ts_rank_cd 仍偏向命中多的文档）。实测"台风预警信号分几级"从 0 结果修复为正常召回。

**Q6：为什么全文路只查中文，英文不做全文？**
A：语料一半是英文教材，但用户问题是中文，中英词面无法直接对上（全文检索的天然弱项）。英文语料的覆盖由向量英文路（LLM 先把问题译成英文）+ reranker 跨语言精排（冒烟测试实测中文问题对英文文档 0.989）承担，避免做中英平行词表的重活。

**Q7：混合检索的延迟比纯向量高多少，值不值？**
A：纯向量单路约 0.4s，混合+精排约 1.1s（多两次嵌入 + 全文 + rerank 网络调用），top-1 准确率 3/5 → 5/5。RAG 场景检索是一次性成本、生成是流式感知成本，1s 的检索开销用户无感，答案质量提升是实打实的。优化的余地：嵌入结果缓存、rerank 候选从 20 减到 15。

**Q8：rerank 挂了怎么办？**
A：rerank_chunks 捕获全部异常返回 None，调用方降级用 RRF 排序——精排是增强项不是依赖项，外部 API 故障不能阻断检索主链路（fail-safe 降级）。

**Q9：GIN 索引和 HNSW 索引分别加速什么？**
A：GIN（倒排索引）加速 tsvector 的 `@@` 匹配——从"含词 X 的文档集合"直接取，不用逐行扫；HNSW（近似最近邻图索引）加速向量 `<=>` 距离排序——跳过绝大多数不可能近的向量。一个服务词法、一个服务语义，混合检索两条索引各走各的，互不干扰。

**Q10：为什么候选池是 20 不是 50 或 10？**
A：权衡：rerank 是逐对现算，候选越多延迟越高（50 条约 3 倍延迟）；太少则 RRF 融合的多样性优势体现不出来。20 是两阶段的常见工程值（召回 4 倍于最终 top-5），且实测 1.1s 总延迟可接受。
