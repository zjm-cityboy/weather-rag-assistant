## 三、问题清单（按严重度分级）

### P0 —— 生产阻塞级（面试被问到会扣分的硬伤）

**P0-1 PostgreSQL 连接无池化**
- 位置：`retriever.py _fetch()`（每次查询 `psycopg2.connect` 新建 TCP+认证握手）；`auth.py`/`ask.py` 同模式
- 风险：一次混合检索 = 3 次独立建连；并发下连接数线性膨胀打满 PG `max_connections`
- 业界标准修法：模块级 `psycopg2.pool.SimpleConnectionPool`（10 行改动）；生产再上层 pgbouncer
- 成本：低（半小时）

**P0-2 LangGraph 图每请求重复编译**
- 位置：`ask.py` 生成器内 `graph = build_graph()`
- 风险：`StateGraph` 构建+`compile()` 每次请求重复执行（节点注册/校验/拓扑排序），纯浪费
- 业界标准修法：模块级单例 `_GRAPH = build_graph()`（compile 线程安全可复用）
- 成本：低（3 行）

**P0-3 会话存储是进程内存**
- 位置：`memory/store.py`（`_sessions: dict`）；代码注释自认"第 6 期换 PG"未兑现
- 风险：重启丢全部会话；compose 后端副本>1 时会话错乱；内存无上限（长会话泄漏）
- 业界标准修法：PG `sessions` 表（username+session_id+role+content+时间），读写各一条 SQL
- 成本：中（2 小时，接口不变只换实现——当初抽象对了）

**P0-4 JWT_SECRET 为空时服务照常启动**
- 位置：`config.py`（默认 ""）；`auth.py` 用空密钥也能签发/验证
- 风险：**空密钥=任何人可伪造任意用户 token**，安全配置缺失被静默吞掉
- 业界标准修法：FastAPI 启动事件校验必填配置（`JWT_SECRET`/`API_KEY`/`NEO4J_PASSWORD`），缺失 fail-fast
- 成本：低（20 行）

### P1 —— 应修（性能/安全/可靠性）

**P1-1 嵌入实例每调用重建**：`retriever.get_embeddings()` 每次 new `OpenAIEmbeddings`（含 httpx client 构造）。修法：模块级单例（与 P0-2 同模式）。

**P1-2 SSE 无心跳 + 客户端断开丢记忆**：长流式（>60s）会被代理/负载均衡掐断；用户中途关页面，生成器收到 GeneratorExit，`append_round` 可能不执行。修法：生成器循环里定期 yield 注释行心跳（`: keepalive\n\n`）；记忆写入放 `finally`。

**P1-3 登录无防护**：无失败限流（可暴力破解）、密码仅长度校验。修法：内存计数器按用户名+IP 限 5 次锁 10 分钟（个人项目够用，生产换 Redis）。

**P1-4 print 而非 logging**：无级别、无结构化、无法关闭。修法：`logging` + 级别由 env 控制（30 分钟全量替换）。

**P1-5 LLM 串行链路长**：一次问答 = 分类+改写+生成+追问 4 次串行 LLM（额外 ~1.5-2s 纯等待）。业界做法：**追问生成异步化**（回答完成先 done，followups 单独接口/事件后推）——用户体验提升最明显的一刀。

**P1-6 无自动化测试**：pytest 单测（意图解析、RRF 融合、token 签验这类纯函数）+ GitHub Actions CI。求职项目有 CI 是显著加分项。

## 四、专项：跨语言检索（context 指标低）的业界最优方案对照

**调研来源**：Microsoft 多语言 RAG 指南、NVIDIA 跨语检索实践、APXML 大规模 RAG 架构、Google RAG Engine 文档（链接见 README 外部参考节）。

**业界共识排序**：

1. **根本解：换强多语言嵌入模型**（中英落入同一语义空间，中文查询直接命中英文文档）。共识原话："query translation is a fallback rather than the primary strategy when a good multilingual embedding is available"
2. 过渡解：查询翻译+多路检索（**本项目当前方案**，定位正确）
3. 叠加项：hybrid（稠密+稀疏）✓ 已有、reranker ✓ 已有、语言感知分块 ✓ 已有（jieba）

**对本项目的正确改法**（替代此前的"英文块 LLM 摘要"自创方案）：

> 换 **BGE-M3**（智源，多语检索基准标杆，输出 1024 维——**与现有 pgvector 表维度恰好兼容**）或 multilingual-e5-large，全库一次性重嵌入（2675 次），重跑实验 4/5/7 复测。

**为什么它优于摘要方案**（资源账，面试话术）：
- 摘要方案：1600 次 LLM 生成 + 1600 次重嵌入，且**语料每次更新都要对新块再生成摘要**（持续成本）；LLM 摘要质量引入新噪声源
- 换模型：2675 次嵌入（一次性），零持续成本，无新增噪声；实验 4 的"中文问台风零命中（Hit@10=0）"问题从根上解决，双语查询+RRF 的两路可简化为一路（省一次 LLM 改写调用的延迟和费用）
- 这正是"解决同一问题的两个方案，资源消耗差一个量级"的标准案例

**评估口径注记**：换模型后 context recall 若仍低于 0.6，剩余部分才是评测语言保守性（英文块 vs 中文参考要点）——届时再考虑评估侧双语 reference，属评测校准而非系统改动。
